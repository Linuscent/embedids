## The challenge

Picture a battery-powered sensor or a small vision module: a Zephyr
application accepts commands, runs inference, ships results upstream and
reports its own health. Attacks against it look like this:

| Threat | What happens on the device |
|--------|----------------------------|
| **Command and state abuse** | An inference or management command arrives in a state that forbids it |
| **Request flooding** | Requests arrive faster than the inference worker can serve them, and its queue overflows |
| **Configuration tampering** | A protected setting changes outside the approved update path |
| **Unexpected outbound activity** | Data heads to an unapproved destination, or approved traffic exceeds its budget |
| **Monitor disruption** | Security telemetry stops, or monitoring samples are lost |

The constraints matter as much as the threats. Detection cannot allocate
memory at run time, interrupt handlers cannot wait for it, and it must never
delay the inference path it protects.

## The approach: detection compiled into the firmware

EmbedIDS joins the build as an ordinary Zephyr module. The C core stays free
of operating-system calls; a thin adapter connects it to Zephyr's kernel:

- **Configured with Kconfig.** Limits such as the number of metrics and the
  queue size reach both the library and its callers, so every structure
  layout matches.
- **Non-blocking ingestion.** `embedids_zephyr_submit()` copies a sample into
  a statically allocated `k_msgq` without waiting. It is safe from threads and
  interrupt handlers. A full queue counts a drop instead of blocking.
- **A single owner.** Only the detector thread touches the EmbedIDS context.
  `embedids_zephyr_poll()` drains at most one queue's worth of samples per
  call, so a burst cannot stall the thread indefinitely.
- **Every sample is evaluated.** All rules run after each queued sample, so a
  normal reading that arrives later cannot hide a brief violation.
- **Unsafe configurations are refused.** The adapter rejects duplicate metric
  names, out-of-range indices, the unfinished built-in trend algorithm and
  Boolean thresholds, rather than running them silently.

## Architecture

The replay above shows the pipeline: application threads on the left, the
32-slot queue in the middle and the detector's rules on the right. Enabling it
takes a few Kconfig lines:

```ini title="prj.conf"
CONFIG_EMBEDIDS=y
CONFIG_EMBEDIDS_ZEPHYR_ADAPTER=y
CONFIG_EMBEDIDS_MAX_METRICS=8
CONFIG_EMBEDIDS_SAMPLE_QUEUE_SIZE=32
CONFIG_EMBEDIDS_FLOATING_POINT=n
```

Producers submit; the detector thread drains and evaluates. In the demo, the
detector thread itself samples the application's counters every 100 ms:

```c title="examples/zephyr/edge_ai_security/src/main.c (simplified)"
while (true) {
    k_sleep(K_MSEC(SAMPLE_MS));            /* 100 ms */
    read_counters_under_lock(values);
    for (uint16_t i = 0; i < METRIC_COUNT; ++i) {
        embedids_zephyr_submit(&detector, i, (embedids_metric_value_t){.u32 = values[i]});
    }
    embedids_zephyr_poll(&detector, detection_result, NULL);
}
```

The demo firmware watches eight rules, all numeric thresholds:

| Rule | Raises an alert when |
|------|----------------------|
| `state_abuse` | a command arrives in a state that forbids it |
| `request_rate` | more than 32 inference requests arrive in one interval |
| `queue_rejects` | the eight-slot inference queue rejects a request |
| `config_integrity` | the work-unit setting differs from its approved value |
| `unknown_destination` | a send targets an unapproved destination |
| `tx_volume` | more than 4,096 approved bytes leave in one interval |
| `heartbeat_age` | the telemetry producer's last heartbeat is older than 500 ms |
| `telemetry_drops` | the adapter's sample queue drops a sample |

Each alert is printed once, when the rule starts failing, with the value, the
limit and the sample time. A `clear` line follows when it recovers.

## Seeing it work

Every scenario boots fresh firmware and types commands into its UART console,
exactly as an operator or an attacker on that interface would.

### Scenario A: a request flood

The device is switched to `active`, then asked for 256 inferences at once.
Nine requests are accepted, one straight to the waiting worker and eight
into its queue, and **247 are rejected**. The next detector sample, 100 ms
after the command, raises two alerts:

```json title="UART output"
{"type":"alert","rule":"request_rate","value":256,"limit":32,"timestamp_ms":440,"sample_ms":100}
{"type":"alert","rule":"queue_rejects","value":247,"limit":0,"timestamp_ms":440,"sample_ms":100}
```

The worker keeps serving the requests it accepted. The detector reads
counters and never touches the request queue itself.

### Scenario B: configuration tampering

The `config` command changes the inference work units, but only while the
device is idle. The test-only `fault config` command bypasses that path and
writes `100` over the approved `10`, as memory corruption or a rogue code
path would. The next sample, **10 ms later**, raises `config_integrity`.

This is an in-memory comparison against the approved value. It shows the
detection path, not cryptographic attestation.

### Scenario C: the telemetry goes silent

`fault heartbeat` stops the telemetry producer, which normally beats every
50 ms. Its age climbs until a sample reads **580 ms**, past the 500 ms limit.
Across ten runs the alert arrived 29 to 79 ms after the timeout expired,
depending on where the silence began within the 100 ms sampling cycle.

### More scenarios

| Scenario | Command | What EmbedIDS raises |
|----------|---------|----------------------|
| State abuse | `infer 1` while idle | `state_abuse` after 10 ms |
| Unknown destination | `send unknown 128` | `unknown_destination` after 10 ms |
| Outbound volume | `send approved 8192` | `tx_volume` after 100 ms |
| Queue overflow | `fault overflow` | `telemetry_drops` after 120 ms, 104 samples dropped |
| Normal workload | 12 paced `infer 1` and `send approved 256` | Nothing; 12 inferences completed |

The normal run also sends seven malformed commands, such as `infer 257`. The
parser rejects them without raising alerts: bad syntax is not, by itself,
evidence of an attack.

## Results

<DetectionBudget />

- **7 / 7 scenarios passed** in each of 10 repeated runs, including the
  normal workload with no alerts.
- **10–120 ms** from trigger to alert sample, against a 200 ms budget of two
  sample periods.
- **640 bytes** of metric history: eight metrics, four samples each, 20 bytes
  per sample.
- **19 / 19 tests** for the Zephyr adapter, across integer and
  floating-point builds.

| Measure | Target | Measured |
|---------|--------|----------|
| Scenario acceptance | 7 / 7 | 7 / 7 in every one of 10 runs |
| Trigger to alert sample | ≤ 200 ms | 10–120 ms |
| Alerts during the normal workload | 0 | 0 |
| Heap allocation in the detector and adapter | none | no allocator symbols referenced |
| Metric history | — | 640 B |
| Adapter state, including the 32-slot queue | — | 872 B |
| Host CPU for the whole simulated firmware | — | 1.4–1.9 % of one core |

The host CPU figure covers the entire `native_sim` process on an x86-64
host. It is not a microcontroller measurement, and native executable sizes
are not flash budgets.

The integration is backed by automated checks that run in CI:

- **Adapter tests** cover per-sample evaluation, interrupt-context
  submission, concurrent producers, overflow accounting, history
  wrap-around, invalid configurations, custom algorithms, and builds with
  floating-point and double-precision metrics.
- **The scenario runner** boots fresh firmware for each scenario and drives
  its UART. It fails on a missing alert, an unexpected alert, or a detection
  slower than 200 ms.
- **A no-fault build** confirms that the fault commands disappear when
  `CONFIG_EMBEDIDS_DEMO_FAULT_INJECTION` is off.
- **The core library's** existing test suites run in the same workflow.

## What we learned

- **Evaluate every sample, not just the latest.** The first adapter drained
  the whole queue and then checked each metric once, so a normal reading
  could mask a violation queued just before it. The adapter now runs every
  rule after each sample, and a regression test pins this down.
- **A drop counter must not depend on the queue it measures.** In the
  overflow scenario, the report of the first 96 drops was itself dropped,
  because the queue was full. The alert came one interval later from the next
  count, still within budget. The fix is to read `embedids_zephyr_dropped()`
  directly in the detector instead of routing it through the queue.
- **Counts per interval are not rates.** Thresholds apply per observed
  interval. Under scheduling delays, intervals stretch; production firmware
  should measure the interval and the detector's own deadline.
- **A monitor cannot report its own death.** Heartbeat detection catches a
  silent producer while the detector runs. A stalled detector or device needs
  a hardware watchdog or an external observer.

## What this study does not show

- **Hardware behavior.** Timing on `native_sim` is simulated and almost
  deterministic; a physical board adds interrupt and scheduling jitter.
- **Real inference or networking.** The workload and the dispatcher model
  application policy; no neural network runs and no packets are inspected.
- **Protection against privileged compromise.** Everything shares one trusted
  firmware image. There is no userspace isolation, secure-world monitor or
  automatic containment.
- **A field false-positive rate.** A short scripted normal workload with no
  alerts is a regression check, not a statistical claim.

## Try it yourself

The demo needs a Linux host with a Zephyr v4.2.0 development environment;
no hardware is required.

<Tabs>
<TabItem label="Scenarios">

```bash

python3 scripts/zephyr/run_scenarios.py \
  --binary build/zephyr-demo/zephyr/zephyr.exe \
  --report build/zephyr-demo/scenarios.json
```
